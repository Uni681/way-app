# 審査キュー・通知制限の適用手順

この文書とSQLはレビュー用。今回、本番のDB・設定・デプロイは一切変更していない。

## 適用前

1. 独立したステージングを用意する。DBバックアップと既存policy/列grant/RPC grantの一覧を保存し、009までの前提と照合する。未知の権限、独自トリガー、API公開schemaがある場合は差分をレビューする。
2. `private` schemaをData APIの公開schemaに追加しない。service-role・CRON_SECRET・Vaultの値をブラウザー、Git、ログに出さない。
3. 既存messagesの非削除pending/passed件数を数え、再審査時間と外部AI費用を見積もる。010は過去のpassedも信用せずpendingへ戻す。再承認までは相手には見えない。既に端末へ配信された過去本文を取り消せるわけではない。
4. 旧い会話回数・図鑑・課金状態が信頼できるか別途確認する。今回のmigrationはそれらを自動リセットしない。過去メッセージはcounted扱いにして再審査の二重加算を防ぐ。
5. 既存のcron `notify-expiring-chats` 等がある場合は記録し、切替時の停止対象を決める。添付インストーラーは自分が管理する3名称のみ置き換える。

## ステージングの切替

1. 投稿を停止したメンテナンス時間内に、未適用の009、その後010・011・012を順番に適用する。各ファイルはトランザクション単位。既存schema全体や過去migrationの再実行はしない。
2. 新しいAPIと画面を同時にステージングへ配置する。新画面は本人情報をget_my_profileから取得し、送信中・再試行・保留を表示する。旧画面は非公開プロフィールSELECTが拒否されるため再読み込みが必要。
3. サーバーに32文字以上のランダムな`CRON_SECRET`を設定する。Supabase Vaultへ`way_worker_base_url`（ステージングURL）、`way_worker_cron_secret`（同じsecret）を登録する。値の作成・入力は秘密管理画面で行う。
4. ステージングでpg_cron、pg_net、Vaultを利用可能にし、`supabase/operations/install_security_workers.sql`を実行する。審査・タイマーは毎分、頻度カウンター掃除は毎時。SQL中にsecretの平文は保存しない。
5. `/api/moderation/worker`は1要求あたり最大3件、1件のAIタイムアウト15秒、最大実行時間60秒を想定。ホスティングがこの時間を許容するか確認する。インストーラーのHTTPタイムアウトは55秒。1分3件が初期処理能力なので、履歴量や投稿量が上回る場合はグローバル上限60 claim/分の範囲でワーカー起動数を調整する。
6. 同名タスクの重複起動でもclaim/通知予約の一意性が効くことを、実PostgreSQLの独立接続で確認する。pg_cronの起動成功だけでなく、pg_netのHTTP応答を確認する。

## 必須の受入確認

- 送信者、相手、第三者、未認証の4セッションを準備する。ブラウザーのmoderate API呼び出しを完全に止めて直接messagesへ投稿してもキューができ、ワーカーだけで処理されること。
- 初回SELECT、Realtime、再接続、別タブ、5秒ポーリングのすべてで、相手にpending/retry/held本文が一度も表示されないこと。送信者には未送信表示があること。
- AI障害は30秒・60秒の再試行後に保留すること。タイムアウト・通信断・ワーカー停止は保留になり、相手に配信されないこと。
- 同一IDの並行claimが一件だけ通り、古いlease tokenや一般ユーザーの完了RPCが拒否されること。審査を通すまで会話回数・図鑑を増やせないこと。
- 通知を同一イベントで並行連打しても1回だけ予約されること。失敗後・ワーカー再起動後も同じイベントを再送しないこと。異なるイベントの連打も分/時間上限で止まること。
- 他人の購読/通知設定/職業/課金情報を直接SELECTやjoinで読めないこと。本人RPCには他人のIDを渡せないこと。本人の通常のプロフィール変更・ルール同意は継続して動くこと。
- voice状態/期限/チャットID、課金状態、審査状態、図鑑、通報状態を一般ユーザーが偽装できないこと。期限切れ/BANのマッチングと無関係な対象の通報・ストックを拒否すること。
- 無料/有料ドリンク、期限内/自由チャット、Stripeテストモード、実機Pushを確認する。メロンソーダ数は実ドリンクINSERTから一度だけ増えること。
- RealtimeのpublicationとREPLICA IDENTITYを確認する。010でmessagesはDEFAULTにする。過去行の全文を通知する独自Broadcast/ビューが存在しないこと。

## 監視と保留解除

`supabase/operations/security_health.sql`は管理者用の読み取り診断で、本文・秘密値を出力しない。queued/retryの最古時刻、held件数、期限切れlease、HTTP応答、通知reserved/failed件数を監視する。最古のqueuedが2分以上、heldが1件以上、連続HTTP非2xxを初期アラートの目安とし、処理能力に合わせて見直す。通知は失敗レコードを保持する。

保留の手動再試行は、外部AIと旧ワーカーが終了したことを確認してから、管理者が対象IDを指定して`public.retry_held_moderation(uuid)`を呼ぶ。本文を変更して承認済みにする運用はしない。再試行回数はリセットされるので、無制限の一括再試行は避ける。

通知は送信前予約方式のため、プロセス停止や通信結果不明時に未達になり得る。予約・送信台帳を削除して再送すると重複し得るので、自動削除・自動再送しない。受取端末側までの厳密な一回配信は保証しない。

## 本番適用と切り戻し

本番適用は、このステージングの結果・バックログ処理計画・運用監視の確認後に別途承認する。本PRを作成しただけではcronもmigrationも適用されない。

問題が出た場合は投稿とworkerスケジュールを停止し、本文の公開条件は維持する。安全に処理できない投稿は非公開のまま保留する。RLSを外してpendingを公開する切り戻しや、旧moderateの無認証管理更新へ戻す切り戻しは行わない。migrationの列・キュー・配信台帳の削除はデータ損失/重複の原因となるため、単純なdown SQLは提供しない。
